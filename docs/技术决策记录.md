## ADR-001：数据库用 better-sqlite3 + Drizzle ORM，不用 Prisma

- **日期**：2026-08-02（M1 启动）
- **状态**：已采纳
- **背景**：PRD §6.1 原写 Prisma。但本项目第一约束是「全靠 AI 生成代码、出错率低」。Prisma 的 query engine 是二进制，在 Electron 打包进 `app.asar` 后无法执行，必须 `asarUnpack` 解包并修正运行时路径（社区 issue [#9613](https://github.com/prisma/prisma/issues/9613) 至今未官方完美解决）。
- **决策**：改用 **better-sqlite3（同步、native，但 Electron 打包只需常规 asarUnpack，成熟稳定）+ Drizzle ORM**（TS 类型安全、schema-first、迁移工具齐全）。
- **否决项**：
  - Prisma——打包踩坑率高，AI 看不见运行时二进制路径错误，调试痛。
  - better-sqlite3 裸 SQL——失去 schema 迁移和类型推导，表一多就累。
- **后果**：
  - 打包配置 `asarUnpack` 需含 better-sqlite3 的 `.node` 文件。
  - Drizzle 生态略小于 Prisma，但完全够用。
- **何时可推翻**：若 Prisma 推出官方 Electron 一等支持（无 asar 路径问题），可重评估。

### ⚠️ 实施补充（M1 实测，2026-08-02）
- **better-sqlite3 版本必须 ≥ 13.x**。最初装 11.10，在 electron-builder 触发 `@electron/rebuild` 针对 Electron 42（很新的 V8）重编译时报 `v8::External::Value` 不接受 0 参数的源码不兼容错误。升级到 13.0.2 后 rebuild 一次通过。
- 打包后 app.asar.unpacked 中存在 `prebuilds/win32-x64.node` + `build/Release/*.node`，运行时 `[db] 已初始化` 日志确认能加载，app.db 在 userData 正常生成（含 WAL）。
- **AGENTS.md 禁忌需补一条**：better-sqlite3 锁 ≥13.x。

## ADR-002：联网搜索 Tavily + Bing 双 provider 都接

- **日期**：2026-08-02
- **状态**：已采纳（M5 实现，M1 预留接口）
- **背景**：PRD §10 TV-3 原问"选哪家"。Tavily 对 LLM 友好有免费额度，但国内可达性需本机验证；Bing 结果全、国内最稳但需 Azure 订阅。
- **决策**：**两家都接**，设置里可切换。`searchTools.ts` 做适配层抽象，内部按 provider 路由。
- **否决项**：只接一家——任一家单独都有可达性/配额风险。
- **后果**：M5 多写一层适配器和两套结果归一化逻辑，工作量增加约 0.5 里程碑。
- **何时可推翻**：若长期只用一家，可删另一家减少维护面。

### ⚠️ 实施补充（M5 搜索半，2026-08-03）
- **本轮只实现 Tavily**。理由：小步验证原则（AGENTS.md §7）——先让单家跑通再叠第二家。Tavily 对 LLM 友好、REST 简单，作为首块验证成本最低。
- **Bing 留待国内可达性确认后补**。架构已预留扩展位：`searchProviders.type` 是 enum（当前 `['tavily']`），`searchTools.searchWithTavily` 是独立 adapter 函数，`factory.getActiveSearchConfig()` 按 type 分支路由——加 Bing 时只需：扩 enum、加 `searchWithBing`、扩路由，不改既有调用链。
- **Tavily API 鉴权方式**：用 `Authorization: Bearer <key>` header（context7 拉的最新 2026-08 规范），非旧的 body 里传 `api_key`。
- **结果归一化**：Tavily 返回的 `results[]` 统一映射成 `{title, url, content, score?, publishedDate?, truncated?}`，对外屏蔽 provider 差异。content 超 1000 字截断并标 `truncated`（token 预算硬控，不暴露给模型）。
- **真机实测**：Tavily 国内可达，搜索-生成-标注来源链接全链路通过（PRD §7.1 V-I 验收达成）。

## ADR-003：模型调用统一 OpenAI SDK 的 chat.completions，不用 responses API

- **日期**：2026-08-02
- **状态**：已采纳
- **背景**：OpenAI 官方主推新的 `responses` API。但实测确认：智谱 GLM、DeepSeek 的 OpenAI 兼容端点**只支持老的 `chat.completions`**，新的 `/responses` 尚未支持（智谱有 GitHub issue #39 在跟进）。
- **决策**：所有模型调用统一走 `client.chat.completions.create({ stream, tools })`。
- **否决项**：responses API——国产兼容端点不支持，会导致整个模型层不可用。
- **后果**：拿不到 responses API 的新特性（多 agent、内置工具等），但 v1 范围不需要。
- **何时可推翻**：智谱/DeepSeek 兼容端点完整支持 responses 后，可逐 provider 迁移。

## ADR-004：首期交付范围 = M1 骨架 + 技术验证（Tracer Bullet）

- **日期**：2026-08-02
- **状态**：已采纳
- **背景**：用户最初指令"生成完整代码"与 PRD §6.4 方法论"小步生成+逐步验证，不允许一次性生成大块"冲突。
- **决策**：先做 M1——打穿最险链路（electron-vite→模型→流式→FC→落库），证明后续走得通，再按 M2~M7 推进。

- **何时可推翻**：若 M1 异常顺利且用户希望加速，可在某里程碑合并多步。

## ADR-006：主进程加全局未捕获异常兜底

- **日期**：2026-08-03（M5 搜索半）
- **状态**：已采纳
- **背景**：真机实测联网搜索时，生成内容阶段偶发弹出两个相同的原生报错窗口。日志显示搜索本身 6 次全部成功、无 `[ERROR]`，判断是**未捕获的 Promise rejection**（最大嫌疑是 OpenAI SDK 4.x 流式迭代器在连接抖动时抛出的、未被 await 链接住的内部 rejection）。Electron 默认对这类未捕获事件弹原生窗口，体验差。
- **决策**：主进程入口（`main/index.ts`）注册 `process.on('uncaughtException')` + `process.on('unhandledRejection')`，**捕获后写日志（`logError` 到 userData/app.log），不弹原生窗口**。
- **否决项**：
  - 保持默认（弹原生窗口）——偶发网络抖动会打断用户生成，体验极差。
  - 只修具体调用点——根因偶发难复现，且不知道还有哪些调用点未来会踩，兜底是最后防线。
- **后果**：
  - 这是**兜底**，不替代具体调用点的 try/catch。根因治理仍应在调用点（如 chat.ts 流式迭代、onToken 的 webContents.send）单独保护。
  - 真正排障看 `userData/app.log` 的 `[ERROR]` 行。
  - 加固后真机复测：日志 0 个 ERROR，原生弹窗消失，生成正常。
- **何时可推翻**：若引入了更完善的应用级错误监控（如 M7 日志轮转 + 分级），可替换此兜底。

## ADR-007：Task 表建表时预埋 M4/M6 字段，但不建 remindTimes

- **日期**：2026-08-03（M3 任务基础）
- **状态**：已采纳
- **背景**：M3 只做手动 Task CRUD（PRD §7.1 V-D）。但 PRD §4.2 Task 模型含 `source`/`sourceConversationId`（M4 抽取溯源）、`followupLog`（M6 跟进日志）、`remindTimes`（M6 跟进时间点）。M3 建表时要决定哪些字段现在建、哪些留到对应里程碑。
- **决策**：
  - **现在建**：`source(manual/from_chat)`、`sourceConversationId`、`followupLog`。理由：这些是普通可空列，建表时带上零成本；M4 抽取入库填 `source='from_chat'`、M6 跟进追加 `followupLog` 都无需 ALTER TABLE，接口天然对齐。
  - **暂不建**：`remindTimes`。理由：SQLite 无数组类型，需 JSON-in-text 或子表两种方案，属 M6 跟进调度的设计范畴，现在定会过度设计；M6 真做时按实际需求选型再加列。
- **否决项**：
  - 全部字段现在建（含 remindTimes）——提前为不确定的需求定型，违背 YAGNI。
  - 只建 M3 必需字段，M4/M6 再 ALTER——SQLite 的 ALTER TABLE 支持有限（不能改列约束/默认值），老用户库迁移麻烦，预建可空列更稳。
- **后果**：M3 TaskInput 不暴露 source/sourceConversationId/followupLog（服务端 upsert 时写死 source='manual'）；M4/M6 通过各自的入口写这些字段。
- **何时可推翻**：M6 实现跟进调度时，若发现 followupLog 的追加式语义需要结构化（如带时间戳的多条记录），可改成子表。

## ADR-008：对话落库粒度与渲染层「合并式语义」对齐

- **日期**：2026-08-03（M2 对话历史持久化）
- **状态**：已采纳
- **背景**：M2 要把对话历史落库。`chat.ts` 的 FC 循环里 `working` 数组每轮会 push assistant + tool 消息（多轮），但渲染层 ChatPage 把所有轮的 assistant 文本**拼成一条 aiMsg.content**（合并式语义）。落库粒度有两个选择：(A) 按 working 逐轮拆成多条 message 行；(B) 与渲染层对齐，一轮对话落 1 user + 1 assistant（合并文本 + toolCalls 数组）。
- **决策**：选 (B)。一轮对话落 2 条 message 行：1 条 `role=user`（最后那条 user）+ 1 条 `role=assistant`（`content`=所有轮文本拼接，`toolCalls`=所有轮工具调用数组）。中间的 `role=tool` 结果消息**不落库**。
- **理由**：
  - 与渲染层 1:1 对应：hydrate 时 DB 行 → ChatMessage 直接映射，无需合并/拆分逻辑。
  - 中间 tool 消息是模型上下文用的临时态，渲染层从不显示，历史回放也不需要——它们的价值只在"当时让模型继续生成"，落库无意义。
  - `chat.ts` 加 `ChatResult` 返回值（`{finalText, toolCalls}`）把跨轮累积的信息吐出来，**FC 循环控制流完全不动**，风险最低。
- **否决项**：
  - (A) 逐轮拆——hydrate 要把多行合并成一条显示，且中间 tool 行要过滤，复杂度高；历史回放语义和实时对话不一致。
  - 流式 token 逐 chunk 落库——写库频率极高，性能差且无必要（最终文本一条就够）。
- **后果**：落库的 assistant 消息 content 是"合并文本"，单看一条就能看到完整回复；toolCalls 是数组（JSON 列）。`message:insert` IPC 供 chat:send 内部落库用。
- **何时可推翻**：若未来要支持"重新生成某一轮"或"编辑历史某条消息"，可能需要更细粒度（按轮拆）。届时改 persistTurn + hydrate 映射即可，表结构不用动（messages 行本来就是任意粒度）。

## ADR-009：上下文截断用字符数估算 token，不引入 tokenizer

- **日期**：2026-08-03（M2 上下文截断）
- **状态**：已采纳
- **背景**：M2 要按 token 预算截断历史（CONTEXT.md「上下文预算」）。准确计数需要 tokenizer（如 tiktoken/js-tiktoken）。但：(1) tiktoken 依赖 wasm 文件，在 Electron asar 内打包/加载可能踩坑（类似 better-sqlite3 native 的问题）；(2) 国产模型（智谱/DeepSeek）的 tokenizer 和 GPT 的 tiktoken 不完全一致，用 tiktoken 计数本身也不准。
- **决策**：用 `字符数 × 1` 作为 token 的保守上界估算（`truncate.ts`）。截断阈值默认 32k。
- **理由**：
  - 截断的目的是**不超模型上限**，估多了（保守）只会多丢几条旧消息，不会超限——安全方向。
  - 零依赖，规避 wasm 打包风险，符合项目"出错率低"第一约束。
  - 估算偏差可接受：中文 1 字约 0.6-1 token，×1 是上界；英文偏松但混合内容仍安全。
- **否决项**：
  - 引入 js-tiktoken——打包风险 + 对国产模型不准，收益不抵成本。
  - 按消息条数截断——长消息和短消息差异大，条数无法反映真实 token 占用。
- **后果**：截断会比"精确 tokenizer"早触发一点（多丢 1-2 条旧消息），用户体验上无感知（被丢的是最早的历史）。`truncateByTokenBudget` 返回 `dropped` 数，主进程推 `chat:truncated` 事件让 UI 提示（禁忌：不静默丢）。
- **何时可推翻**：若发现某模型因估算偏差导致超限报错，可把系数从 1 调到 1.3 或 1.5（更保守）。若要精确，再评估 tokenizer 方案。

## ADR-010：任务抽取走独立 IPC 非流式调用，不做成 FC 工具

- **日期**：2026-08-03（M4 对话→任务）
- **状态**：已采纳
- **背景**：M4 要让 AI 从对话识别待办任务。两种实现路径：(A) 抽取作为一个 FC 工具注册进 `assembleTools`，模型在对话中自主调用 `extract_tasks` 返回草稿；(B) 抽取作为独立 IPC（`task:extract`），渲染层触发时主进程单独起一个非流式模型调用。
- **决策**：选 (B)。抽取走独立非流式调用（照搬 `provider:test` 范式），不做成 FC 工具。
- **理由**（四条硬约束都指向 B）：
  1. **AGENTS.md §6 红线**："不要静默建任务。任务抽取只产草稿，必须人工点'加入任务'才入库。" FC 工具是模型自主调用即产生副作用，与"必须人工确认"的语义天然别扭。
  2. **CONTEXT.md「任务抽取草稿」**："用最便宜的模型跑，省成本。" FC 走对话主模型，无法切换到更便宜的抽取专用模型。独立调用可从 settings 读 `extract.providerId` 指定。
  3. **触发方式**："默认手动（点 ✨ 按钮）"——离散 UI 动作，不是模型自主决策。
  4. **AGENTS.md §2 目录**：预留 `services/taskExtractor.ts` 独立文件，而非塞进工具集。
- **否决项**：
  - (A) FC 工具——与上述四条约束冲突；且塞进 FC 循环后草稿和对话回复混在一轮，打乱落库语义（persistTurn 一次落 user+assistant）。
- **后果**：`taskExtractor.ts` 一个函数 `extractTasks(providerId, messages)`，内部 `createClientForProvider` + 非流式 `chat.completions.create({stream:false})`。草稿不入库，用户确认后走 `task:create_from_draft`（source 强制 from_chat）。FC 循环（chat.ts）完全不动。
- **何时可推翻**：若未来要支持"模型在对话中主动建议任务"（而非用户点按钮），可评估 FC 方案，但仍要解决"换便宜模型"和"人工确认"两个问题。

## ADR-011：跟进会话主进程内部 insert，不走 conversation:create IPC

- **日期**：2026-08-03（M6 常驻+定时跟进）
- **状态**：已采纳
- **背景**：M6 到点要创建 type=followup 的跟进会话 + 首条 AI 问候消息。现有 `conversation:create` IPC 是渲染层发起的"user 主动新建"，而跟进会话是"AI 主动发起"（调度器到点触发）。两者发起方不同。
- **决策**：跟进会话由主进程 `runFollowupTick()` 内部直接 `db.insert(conversations)` + `db.insert(messages)`，不走 conversation:create / message:insert IPC。
- **理由**：
  - 发起方是主进程调度器（到点自动触发），不经过渲染层——走 IPC 绕一圈无意义。
  - 首条消息是非流式模型调用生成（照搬 taskExtractor 范式），不是 chat:send 的流式流程——到点时窗口可能关着，流式推给谁。
  - 用户点通知进来后，回复时才走现有 chat:send（复用 confirmMap 二次确认），这时是正常的 user 发起对话。
- **否决项**：复用 conversation:create IPC——它是渲染层调用的，主进程自己调自己违反分层；且 ConversationInput 不接 scenarioId 字段。
- **后果**：scheduler.ts 内部 insert followup 会话 + assistant 消息。去重逻辑（今天已有 followup 会话则复用）也在 scheduler 内部处理。
- **何时可推翻**：若跟进会话需要更复杂的创建逻辑（如关联多个任务、带场景模板），可考虑抽成独立服务函数但仍不走 IPC。

## ADR-012：定时调度用 node-cron

- **日期**：2026-08-03（M6 常驻+定时跟进）
- **状态**：已采纳
- **背景**：M6 需要定时调度器（默认每天 9:00/14:00 检查待办任务）。两种方案：(A) setInterval 每 N 分钟轮询；(B) node-cron 按 cron 表达式定点触发。
- **决策**：选 (B) node-cron。
- **理由**：
  - 符合 CONTEXT.md「默认 09:00、14:00」的定点语义——cron 表达式 `0 9,14 * * *` 精确到点触发。
  - setInterval 轮询触发不精确（误差一个轮询周期），且持续轮询耗电。
  - node-cron 是纯 JS 模块（无 native 依赖），在 Electron asar 内打包无踩坑风险。
  - 用户可在设置页配 cron 表达式（followup.cron），灵活。
- **否决项**：setInterval——触发不精确 + 持续轮询开销。
- **后果**：新增 node-cron 依赖。调度器在 app.whenReady 时启动一次（读 settings 的 cron 表达式），设置改了需重启应用生效（MVP，不做热重载）。
- **何时可推翻**：若发现 node-cron 在打包后异常（目前真机 dev 验证正常），回退到 setInterval。

## ADR-013：v1.2 工具扩展用双轨制（FC + 手动页面）

- **日期**：2026-08-03（M12.5 v1.2 工具扩展）
- **状态**：已采纳
- **背景**：v1.2 加笔记/提醒/番茄钟/文档转换四个工具。每个工具的形态有两种选择：(A) 全做成 FC 工具让 AI 在对话里调；(B) 全做成独立 React 页面让用户手动操作。
- **决策**：**双轨制**（PRD §13.1）。按工具用途选形态：
  - **A 轨（FC）**：笔记 create/search/read/update、提醒 set_reminder、文档转换 convert_document —— 这些在对话里调更自然（"把这段存成笔记"）。
  - **B 轨（手动页面）**：笔记编辑器、提醒列表、番茄钟、转换器 UI —— 这些用户主动操作更顺手（番茄钟做成 FC 无意义）。
- **关键约束**：A 轨与 B 轨**共享同一存储层**（笔记库目录 / reminders 表 / pomodoro_sessions 表）。AI 存的笔记，用户在笔记页能编辑；用户设的提醒，AI 也能查到。这保证双轨不是两套孤立系统。
- **否决项**：
  - 全 FC——番茄钟等计时器/编辑器做成 FC 毫无意义。
  - 全手动页面——"把这段对话存成笔记"还要切页面点按钮太蠢。
- **后果**：每个工具有两套入口（FC + UI），但共享 IPC + 存储层，复用度高，不重复造轮子。

## ADR-014：笔记存储用纯 .md 文件 + frontmatter，不建库表

- **日期**：2026-08-03（M12.7 v1.2 笔记）
- **状态**：已采纳
- **背景**：v1.2 笔记功能要决定存储方案：(A) 建笔记表（类似 tasks）；(B) 纯 .md 文件。
- **决策**：选 (B) 纯 .md 文件 + frontmatter。笔记库目录默认 `userData/notes/`，每条笔记 = 一个 `.md` 文件，frontmatter 存 id/title/tags/时间戳。
- **理由**：
  - **可移植性**：用户能在文件管理器里直接看到、编辑、备份笔记（.md 是通用格式）。
  - **v2 地基**：PRD §13.2 明确这是 RAG 知识库的地基，纯文件方案便于 v2 加索引/向量化。
  - **与文件工具天然协同**：笔记库目录自动加入文件白名单，AI 用现有 read_file/write_file 就能操作，无需专门笔记 IPC（但仍提供 note:* IPC 封装 frontmatter 解析）。
  - **搜索 v1.2 简单**：文件遍历 + 字符串匹配（<500 条够用），v2 加 SQLite 索引层。
- **否决项**：
  - 建库表——失去可移植性，与"第二大脑"愿景冲突。
- **后果**：noteStore.ts 负责 frontmatter 解析/序列化 + CRUD；文件名用 `{slug}.md`（基于 title），冲突追加 -2/-3。

## ADR-015：PDF 生成用 pdfkit + 系统字体 simhei.ttf（TV-4）

- **日期**：2026-08-03（M12.9 v1.2 文档转换，TV-4 验证）
- **状态**：已采纳
- **背景**：v1.2 文档转换要 md→pdf。PRD §15.5 列两个候选：puppeteer-core（依赖系统 Chrome，样式完美）vs pdfkit（纯 JS，样式弱但无外部依赖）。
- **决策**：选 **pdfkit**。
- **理由**：
  - **第一约束（出错率低）**：puppeteer-core 需系统 Chrome/Edge + Electron 额外打包配置，坑多；pdfkit 纯 JS 零外部依赖，Electron 打包零坑。
  - **TV-4 实测**：pdfkit + `C:/Windows/Fonts/simhei.ttf` 中文 PDF 渲染成功（7.7KB 输出）。
  - **已知坑（已规避）**：pdfkit 不支持 `.ttc`（TrueType Collection），只支持 `.ttf`。Windows 雅黑 `msyh.ttc` 用不了，改用 `simhei.ttf`（黑体）。
- **否决项**：
  - puppeteer-core——依赖系统 Chrome，违背"纯本地零配置"理念。
- **后果**：md→pdf 在 converter.ts 用 pdfkit 写纯文本（按行分割，标题大字号），不做完整 HTML→PDF 排版（pdfkit 排版 HTML 复杂，AI 出错率高，简化够用）。

## ADR-016：提醒调度用 setInterval 轮询，不复用 node-cron

- **日期**：2026-08-03（M12.5 v1.2 提醒）
- **状态**：已采纳
- **背景**：v1.2 提醒要定时触发。已有 ADR-012 的 node-cron（跟进调度）。是否复用 cron 做提醒？
- **决策**：提醒用 **setInterval 轮询**（每 60s 扫 reminders 表），不复用 cron。
- **理由**：
  - **语义不同**：跟进是"定点"（9:00/14:00），cron 表达式贴切；提醒是"任意到分"（用户随时设的"N 分钟后"），cron 表达式难以覆盖，轮询语义更贴切。
  - **实现简单**：`setInterval(tick, 60000)` 扫 `time<=now && done=0`，触发后标 done。无需为每个提醒算 cron 表达式。
  - **精度足够**：60s 轮询，提醒最多迟 1 分钟，用户无感。
- **否决项**：
  - 复用 node-cron——提醒时间任意，每条提醒一个 cron 表达式开销大且复杂。
- **后果**：scheduler.ts 加 `startReminderPoller`/`stopReminderPoller`，与 followup cron 并存（两套独立调度）。

## ADR-017：图标库 lucide-react → Phosphor（v1.3 品牌升级）

- **日期**：2026-08-03（M13.2 v1.3 UI 全面重造）
- **状态**：已采纳
- **背景**：v1.2 统一到 lucide-react，但用户反馈「视觉太简，缺品牌感」。ui-ux-pro-max skill 推荐 Phosphor（支持 duotone/fill 多 weight，品牌质感更强）。
- **决策**：换 **Phosphor**（`@phosphor-icons/react`）。
- **理由**：
  - **多 weight 支持**：thin/light/regular/bold/fill/duotone 六档，品牌位用 duotone（双色，有层次），功能位用 regular。lucide 只有单一线条风格。
  - **skill 推荐**：ui-ux-pro-max 完整 bundle 调研结论。
  - **图标映射表**（src/components/ui/icons.ts）做语义化别名（lucide 名 → Phosphor 组件），业务文件 import 路径改一处，图标名不变，迁移成本最低。
- **否决项**：
  - 继续 lucide——品牌提升有限，正是用户不满的点。
  - 自绘 SVG——AI 出错率高，违背第一约束。
- **后果**：14 个业务文件迁移；卸载 lucide-react；IconContext 全局默认（weight=regular size=18）；清理全部 strokeWidth（Phosphor 用 weight 控制粗细）。

## ADR-018：Soft UI 柔和阴影系统（v1.3 层次质感）

- **日期**：2026-08-03（M13.1 v1.3）
- **状态**：已采纳
- **背景**：v1.2 的「无圆角 + hairline」签名风格偏硬，用户反馈「形状太硬，想要柔和/有质感」。ui-ux-pro-max 推荐 Soft UI Evolution 风格。
- **决策**：建立 **Soft UI 阴影系统**（多级 shadow token）+ 适度圆角 + 多级 surface 背景。
- **落地**：
  - `--shadow-xs/sm/md/lg`：柔和多层（一层漫射 + 一层近距投影），模拟自然光浮起感；深色主题用更高透明度黑（浅色阴影在深底发灰）。
  - 多级 surface：`--surface-1`（页面底）/`--surface-2`（卡片层 #FFFFFF）/`--surface-3`（浮层），浅深双主题同步。
  - radius 从 0.25rem 回调 0.5rem（Soft UI 需适度圆角配柔和阴影）。
  - Card/Button 加 shadow-sm + hover 加深 + transition。
- **否决项**：
  - 完全推翻冷调科技风改活泼风——工作量大且违 PRD §12.1 哲学；只加层次不改基调。
- **后果**：全应用卡片有浮起感；@theme inline 覆盖 Tailwind 默认 shadow；grep 仍要求 0 处原生色类（V-O 验收不变）。

## ADR-019：字体 Inter → Space Grotesk + DM Sans（v1.3 品牌识别）

- **日期**：2026-08-03（M13.1 v1.3）
- **状态**：已采纳
- **背景**：Inter 是通用 UI 字体，无品牌识别。ui-ux-pro-max 推荐 Space Grotesk（标题，tech/startup 气质）+ DM Sans（正文）。
- **决策**：标题用 **Space Grotesk**（font-display 变量），正文用 **DM Sans**。
- **理由**：
  - **品牌识别**：Space Grotesk 的几何感 + 略带个性的字形，比 Inter 更有 tech/AI 产品气质，治「缺品牌感」。
  - **本地化**：@fontsource 打包，离线可用（PRD 要求）。
  - **双字体分工**：标题/正文区分，层次更清晰。
- **否决项**：
  - 继续 Inter——正是用户觉得「单调」的一部分。
- **后果**：卸载 @fontsource/inter；装 @fontsource-variable/space-grotesk + @fontsource/dm-sans；新增 `--font-display` 变量；概览页大标题/卡片数字用 font-display。

## 技术验证实测结论（M1）

### TV-1：智谱 GLM 是否支持 Function Calling
- **结论**：✅ **支持**。GLM-4 / 4.5 / 4.5-Air / 4.6 / 5 全系列在 OpenAI 兼容端点 `https://open.bigmodel.cn/api/paas/v4/chat/completions` 上完整支持 `tools` / `tool_choice`，schema 与 OpenAI 一致。
- **唯一限制**：新的 `/responses` API 尚未支持（见 ADR-003），但我们不用它。
- **依据**：[智谱 OpenAI 兼容文档](https://docs.bigmodel.cn/cn/guide/develop/openai/introduction)。
- **影响**：FC 依赖的功能（任务抽取/状态修改/搜索/文件）全部成立，TV-1 风险消除。

### TV-2：智谱 vs DeepSeek 用于抽取/跟进
- **结论**：两者均支持 FC。
  - DeepSeek `deepseek-chat`（V3）支持 FC，社区反馈偶有不稳定，最大输出 8192 tokens；`deepseek-reasoner`（R1）**不支持** tools。
  - 智谱 GLM-4.5-Air / 4-Flash 更适合做廉价后台调用（抽取/跟进）。
- **决策**：跟进/抽取默认走智谱 Flash 档或 deepseek-chat，设置里可指定。

### DeepSeek 兼容性确认
- `baseURL='https://api.deepseek.com'`（或 `/v1`），OpenAI SDK 直接用，model `deepseek-chat`。
- 依据：[DeepSeek API Docs](https://api-docs.deepseek.com/)。

### TV-3：见 ADR-002（两家都接，M5 实现）。
