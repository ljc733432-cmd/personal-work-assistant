## ADR-001：数据库用 better-sqlite3 + Drizzle ORM，不用 Prisma

- **日期**：2026-08-02（M1 启动）
- **状态**：已采纳
- **背景**：PRD §6.1 原写 Prisma。但本项目第一约束是「全靠 AI 生成代码、出错率低」。Prisma 的 query engine 是二进制，在 Electron 打包进 `app.asar` 后无法执行，必须 `asarUnpack` 解包并修正运行时路径（社区 issue [#9613](https://github.com/prisma/prisma/issues/9613) 至今未官方完美解决）。
- **决策**：改用 **better-sqlite3（同步、native，但 Electron 打包只需常规 asarUnpack，成熟稳定）+ Drizzle ORM**（TS 类型安全、schema-first、迁移工具齐全）。
- **否决项**：
  - Prisma——打包踩坑率高，AI 看不见运行时二进制路径错误，调试痛。
  - better-sqlite3 裸 SQL——失去 schema 迁移和类型推导，表一多就累。
- **后果**：
  - 打包配置 `asarUnpack` 需含 better-sqlite3 的 `.node` 文件。
  - Drizzle 生态略小于 Prisma，但完全够用。
- **何时可推翻**：若 Prisma 推出官方 Electron 一等支持（无 asar 路径问题），可重评估。

### ⚠️ 实施补充（M1 实测，2026-08-02）
- **better-sqlite3 版本必须 ≥ 13.x**。最初装 11.10，在 electron-builder 触发 `@electron/rebuild` 针对 Electron 42（很新的 V8）重编译时报 `v8::External::Value` 不接受 0 参数的源码不兼容错误。升级到 13.0.2 后 rebuild 一次通过。
- 打包后 app.asar.unpacked 中存在 `prebuilds/win32-x64.node` + `build/Release/*.node`，运行时 `[db] 已初始化` 日志确认能加载，app.db 在 userData 正常生成（含 WAL）。
- **AGENTS.md 禁忌需补一条**：better-sqlite3 锁 ≥13.x。

## ADR-002：联网搜索 Tavily + Bing 双 provider 都接

- **日期**：2026-08-02
- **状态**：已采纳（M5 实现，M1 预留接口）
- **背景**：PRD §10 TV-3 原问"选哪家"。Tavily 对 LLM 友好有免费额度，但国内可达性需本机验证；Bing 结果全、国内最稳但需 Azure 订阅。
- **决策**：**两家都接**，设置里可切换。`searchTools.ts` 做适配层抽象，内部按 provider 路由。
- **否决项**：只接一家——任一家单独都有可达性/配额风险。
- **后果**：M5 多写一层适配器和两套结果归一化逻辑，工作量增加约 0.5 里程碑。
- **何时可推翻**：若长期只用一家，可删另一家减少维护面。

### ⚠️ 实施补充（M5 搜索半，2026-08-03）
- **本轮只实现 Tavily**。理由：小步验证原则（AGENTS.md §7）——先让单家跑通再叠第二家。Tavily 对 LLM 友好、REST 简单，作为首块验证成本最低。
- **Bing 留待国内可达性确认后补**。架构已预留扩展位：`searchProviders.type` 是 enum（当前 `['tavily']`），`searchTools.searchWithTavily` 是独立 adapter 函数，`factory.getActiveSearchConfig()` 按 type 分支路由——加 Bing 时只需：扩 enum、加 `searchWithBing`、扩路由，不改既有调用链。
- **Tavily API 鉴权方式**：用 `Authorization: Bearer <key>` header（context7 拉的最新 2026-08 规范），非旧的 body 里传 `api_key`。
- **结果归一化**：Tavily 返回的 `results[]` 统一映射成 `{title, url, content, score?, publishedDate?, truncated?}`，对外屏蔽 provider 差异。content 超 1000 字截断并标 `truncated`（token 预算硬控，不暴露给模型）。
- **真机实测**：Tavily 国内可达，搜索-生成-标注来源链接全链路通过（PRD §7.1 V-I 验收达成）。

## ADR-003：模型调用统一 OpenAI SDK 的 chat.completions，不用 responses API

- **日期**：2026-08-02
- **状态**：已采纳
- **背景**：OpenAI 官方主推新的 `responses` API。但实测确认：智谱 GLM、DeepSeek 的 OpenAI 兼容端点**只支持老的 `chat.completions`**，新的 `/responses` 尚未支持（智谱有 GitHub issue #39 在跟进）。
- **决策**：所有模型调用统一走 `client.chat.completions.create({ stream, tools })`。
- **否决项**：responses API——国产兼容端点不支持，会导致整个模型层不可用。
- **后果**：拿不到 responses API 的新特性（多 agent、内置工具等），但 v1 范围不需要。
- **何时可推翻**：智谱/DeepSeek 兼容端点完整支持 responses 后，可逐 provider 迁移。

## ADR-004：首期交付范围 = M1 骨架 + 技术验证（Tracer Bullet）

- **日期**：2026-08-02
- **状态**：已采纳
- **背景**：用户最初指令"生成完整代码"与 PRD §6.4 方法论"小步生成+逐步验证，不允许一次性生成大块"冲突。
- **决策**：先做 M1——打穿最险链路（electron-vite→模型→流式→FC→落库），证明后续走得通，再按 M2~M7 推进。

- **何时可推翻**：若 M1 异常顺利且用户希望加速，可在某里程碑合并多步。

## ADR-006：主进程加全局未捕获异常兜底

- **日期**：2026-08-03（M5 搜索半）
- **状态**：已采纳
- **背景**：真机实测联网搜索时，生成内容阶段偶发弹出两个相同的原生报错窗口。日志显示搜索本身 6 次全部成功、无 `[ERROR]`，判断是**未捕获的 Promise rejection**（最大嫌疑是 OpenAI SDK 4.x 流式迭代器在连接抖动时抛出的、未被 await 链接住的内部 rejection）。Electron 默认对这类未捕获事件弹原生窗口，体验差。
- **决策**：主进程入口（`main/index.ts`）注册 `process.on('uncaughtException')` + `process.on('unhandledRejection')`，**捕获后写日志（`logError` 到 userData/app.log），不弹原生窗口**。
- **否决项**：
  - 保持默认（弹原生窗口）——偶发网络抖动会打断用户生成，体验极差。
  - 只修具体调用点——根因偶发难复现，且不知道还有哪些调用点未来会踩，兜底是最后防线。
- **后果**：
  - 这是**兜底**，不替代具体调用点的 try/catch。根因治理仍应在调用点（如 chat.ts 流式迭代、onToken 的 webContents.send）单独保护。
  - 真正排障看 `userData/app.log` 的 `[ERROR]` 行。
  - 加固后真机复测：日志 0 个 ERROR，原生弹窗消失，生成正常。
- **何时可推翻**：若引入了更完善的应用级错误监控（如 M7 日志轮转 + 分级），可替换此兜底。

## ADR-007：Task 表建表时预埋 M4/M6 字段，但不建 remindTimes

- **日期**：2026-08-03（M3 任务基础）
- **状态**：已采纳
- **背景**：M3 只做手动 Task CRUD（PRD §7.1 V-D）。但 PRD §4.2 Task 模型含 `source`/`sourceConversationId`（M4 抽取溯源）、`followupLog`（M6 跟进日志）、`remindTimes`（M6 跟进时间点）。M3 建表时要决定哪些字段现在建、哪些留到对应里程碑。
- **决策**：
  - **现在建**：`source(manual/from_chat)`、`sourceConversationId`、`followupLog`。理由：这些是普通可空列，建表时带上零成本；M4 抽取入库填 `source='from_chat'`、M6 跟进追加 `followupLog` 都无需 ALTER TABLE，接口天然对齐。
  - **暂不建**：`remindTimes`。理由：SQLite 无数组类型，需 JSON-in-text 或子表两种方案，属 M6 跟进调度的设计范畴，现在定会过度设计；M6 真做时按实际需求选型再加列。
- **否决项**：
  - 全部字段现在建（含 remindTimes）——提前为不确定的需求定型，违背 YAGNI。
  - 只建 M3 必需字段，M4/M6 再 ALTER——SQLite 的 ALTER TABLE 支持有限（不能改列约束/默认值），老用户库迁移麻烦，预建可空列更稳。
- **后果**：M3 TaskInput 不暴露 source/sourceConversationId/followupLog（服务端 upsert 时写死 source='manual'）；M4/M6 通过各自的入口写这些字段。
- **何时可推翻**：M6 实现跟进调度时，若发现 followupLog 的追加式语义需要结构化（如带时间戳的多条记录），可改成子表。

## ADR-008：对话落库粒度与渲染层「合并式语义」对齐

- **日期**：2026-08-03（M2 对话历史持久化）
- **状态**：已采纳
- **背景**：M2 要把对话历史落库。`chat.ts` 的 FC 循环里 `working` 数组每轮会 push assistant + tool 消息（多轮），但渲染层 ChatPage 把所有轮的 assistant 文本**拼成一条 aiMsg.content**（合并式语义）。落库粒度有两个选择：(A) 按 working 逐轮拆成多条 message 行；(B) 与渲染层对齐，一轮对话落 1 user + 1 assistant（合并文本 + toolCalls 数组）。
- **决策**：选 (B)。一轮对话落 2 条 message 行：1 条 `role=user`（最后那条 user）+ 1 条 `role=assistant`（`content`=所有轮文本拼接，`toolCalls`=所有轮工具调用数组）。中间的 `role=tool` 结果消息**不落库**。
- **理由**：
  - 与渲染层 1:1 对应：hydrate 时 DB 行 → ChatMessage 直接映射，无需合并/拆分逻辑。
  - 中间 tool 消息是模型上下文用的临时态，渲染层从不显示，历史回放也不需要——它们的价值只在"当时让模型继续生成"，落库无意义。
  - `chat.ts` 加 `ChatResult` 返回值（`{finalText, toolCalls}`）把跨轮累积的信息吐出来，**FC 循环控制流完全不动**，风险最低。
- **否决项**：
  - (A) 逐轮拆——hydrate 要把多行合并成一条显示，且中间 tool 行要过滤，复杂度高；历史回放语义和实时对话不一致。
  - 流式 token 逐 chunk 落库——写库频率极高，性能差且无必要（最终文本一条就够）。
- **后果**：落库的 assistant 消息 content 是"合并文本"，单看一条就能看到完整回复；toolCalls 是数组（JSON 列）。`message:insert` IPC 供 chat:send 内部落库用。
- **何时可推翻**：若未来要支持"重新生成某一轮"或"编辑历史某条消息"，可能需要更细粒度（按轮拆）。届时改 persistTurn + hydrate 映射即可，表结构不用动（messages 行本来就是任意粒度）。

## ADR-009：上下文截断用字符数估算 token，不引入 tokenizer

- **日期**：2026-08-03（M2 上下文截断）
- **状态**：已采纳
- **背景**：M2 要按 token 预算截断历史（CONTEXT.md「上下文预算」）。准确计数需要 tokenizer（如 tiktoken/js-tiktoken）。但：(1) tiktoken 依赖 wasm 文件，在 Electron asar 内打包/加载可能踩坑（类似 better-sqlite3 native 的问题）；(2) 国产模型（智谱/DeepSeek）的 tokenizer 和 GPT 的 tiktoken 不完全一致，用 tiktoken 计数本身也不准。
- **决策**：用 `字符数 × 1` 作为 token 的保守上界估算（`truncate.ts`）。截断阈值默认 32k。
- **理由**：
  - 截断的目的是**不超模型上限**，估多了（保守）只会多丢几条旧消息，不会超限——安全方向。
  - 零依赖，规避 wasm 打包风险，符合项目"出错率低"第一约束。
  - 估算偏差可接受：中文 1 字约 0.6-1 token，×1 是上界；英文偏松但混合内容仍安全。
- **否决项**：
  - 引入 js-tiktoken——打包风险 + 对国产模型不准，收益不抵成本。
  - 按消息条数截断——长消息和短消息差异大，条数无法反映真实 token 占用。
- **后果**：截断会比"精确 tokenizer"早触发一点（多丢 1-2 条旧消息），用户体验上无感知（被丢的是最早的历史）。`truncateByTokenBudget` 返回 `dropped` 数，主进程推 `chat:truncated` 事件让 UI 提示（禁忌：不静默丢）。
- **何时可推翻**：若发现某模型因估算偏差导致超限报错，可把系数从 1 调到 1.3 或 1.5（更保守）。若要精确，再评估 tokenizer 方案。

## ADR-010：任务抽取走独立 IPC 非流式调用，不做成 FC 工具

- **日期**：2026-08-03（M4 对话→任务）
- **状态**：已采纳
- **背景**：M4 要让 AI 从对话识别待办任务。两种实现路径：(A) 抽取作为一个 FC 工具注册进 `assembleTools`，模型在对话中自主调用 `extract_tasks` 返回草稿；(B) 抽取作为独立 IPC（`task:extract`），渲染层触发时主进程单独起一个非流式模型调用。
- **决策**：选 (B)。抽取走独立非流式调用（照搬 `provider:test` 范式），不做成 FC 工具。
- **理由**（四条硬约束都指向 B）：
  1. **AGENTS.md §6 红线**："不要静默建任务。任务抽取只产草稿，必须人工点'加入任务'才入库。" FC 工具是模型自主调用即产生副作用，与"必须人工确认"的语义天然别扭。
  2. **CONTEXT.md「任务抽取草稿」**："用最便宜的模型跑，省成本。" FC 走对话主模型，无法切换到更便宜的抽取专用模型。独立调用可从 settings 读 `extract.providerId` 指定。
  3. **触发方式**："默认手动（点 ✨ 按钮）"——离散 UI 动作，不是模型自主决策。
  4. **AGENTS.md §2 目录**：预留 `services/taskExtractor.ts` 独立文件，而非塞进工具集。
- **否决项**：
  - (A) FC 工具——与上述四条约束冲突；且塞进 FC 循环后草稿和对话回复混在一轮，打乱落库语义（persistTurn 一次落 user+assistant）。
- **后果**：`taskExtractor.ts` 一个函数 `extractTasks(providerId, messages)`，内部 `createClientForProvider` + 非流式 `chat.completions.create({stream:false})`。草稿不入库，用户确认后走 `task:create_from_draft`（source 强制 from_chat）。FC 循环（chat.ts）完全不动。
- **何时可推翻**：若未来要支持"模型在对话中主动建议任务"（而非用户点按钮），可评估 FC 方案，但仍要解决"换便宜模型"和"人工确认"两个问题。

## ADR-011：跟进会话主进程内部 insert，不走 conversation:create IPC

- **日期**：2026-08-03（M6 常驻+定时跟进）
- **状态**：已采纳
- **背景**：M6 到点要创建 type=followup 的跟进会话 + 首条 AI 问候消息。现有 `conversation:create` IPC 是渲染层发起的"user 主动新建"，而跟进会话是"AI 主动发起"（调度器到点触发）。两者发起方不同。
- **决策**：跟进会话由主进程 `runFollowupTick()` 内部直接 `db.insert(conversations)` + `db.insert(messages)`，不走 conversation:create / message:insert IPC。
- **理由**：
  - 发起方是主进程调度器（到点自动触发），不经过渲染层——走 IPC 绕一圈无意义。
  - 首条消息是非流式模型调用生成（照搬 taskExtractor 范式），不是 chat:send 的流式流程——到点时窗口可能关着，流式推给谁。
  - 用户点通知进来后，回复时才走现有 chat:send（复用 confirmMap 二次确认），这时是正常的 user 发起对话。
- **否决项**：复用 conversation:create IPC——它是渲染层调用的，主进程自己调自己违反分层；且 ConversationInput 不接 scenarioId 字段。
- **后果**：scheduler.ts 内部 insert followup 会话 + assistant 消息。去重逻辑（今天已有 followup 会话则复用）也在 scheduler 内部处理。
- **何时可推翻**：若跟进会话需要更复杂的创建逻辑（如关联多个任务、带场景模板），可考虑抽成独立服务函数但仍不走 IPC。

## ADR-012：定时调度用 node-cron

- **日期**：2026-08-03（M6 常驻+定时跟进）
- **状态**：已采纳
- **背景**：M6 需要定时调度器（默认每天 9:00/14:00 检查待办任务）。两种方案：(A) setInterval 每 N 分钟轮询；(B) node-cron 按 cron 表达式定点触发。
- **决策**：选 (B) node-cron。
- **理由**：
  - 符合 CONTEXT.md「默认 09:00、14:00」的定点语义——cron 表达式 `0 9,14 * * *` 精确到点触发。
  - setInterval 轮询触发不精确（误差一个轮询周期），且持续轮询耗电。
  - node-cron 是纯 JS 模块（无 native 依赖），在 Electron asar 内打包无踩坑风险。
  - 用户可在设置页配 cron 表达式（followup.cron），灵活。
- **否决项**：setInterval——触发不精确 + 持续轮询开销。
- **后果**：新增 node-cron 依赖。调度器在 app.whenReady 时启动一次（读 settings 的 cron 表达式），设置改了需重启应用生效（MVP，不做热重载）。
- **何时可推翻**：若发现 node-cron 在打包后异常（目前真机 dev 验证正常），回退到 setInterval。

## ADR-013：v1.2 工具扩展用双轨制（FC + 手动页面）

- **日期**：2026-08-03（M12.5 v1.2 工具扩展）
- **状态**：已采纳
- **背景**：v1.2 加笔记/提醒/番茄钟/文档转换四个工具。每个工具的形态有两种选择：(A) 全做成 FC 工具让 AI 在对话里调；(B) 全做成独立 React 页面让用户手动操作。
- **决策**：**双轨制**（PRD §13.1）。按工具用途选形态：
  - **A 轨（FC）**：笔记 create/search/read/update、提醒 set_reminder、文档转换 convert_document —— 这些在对话里调更自然（"把这段存成笔记"）。
  - **B 轨（手动页面）**：笔记编辑器、提醒列表、番茄钟、转换器 UI —— 这些用户主动操作更顺手（番茄钟做成 FC 无意义）。
- **关键约束**：A 轨与 B 轨**共享同一存储层**（笔记库目录 / reminders 表 / pomodoro_sessions 表）。AI 存的笔记，用户在笔记页能编辑；用户设的提醒，AI 也能查到。这保证双轨不是两套孤立系统。
- **否决项**：
  - 全 FC——番茄钟等计时器/编辑器做成 FC 毫无意义。
  - 全手动页面——"把这段对话存成笔记"还要切页面点按钮太蠢。
- **后果**：每个工具有两套入口（FC + UI），但共享 IPC + 存储层，复用度高，不重复造轮子。

## ADR-015：PDF 生成用 pdfkit + 系统字体 simhei.ttf（TV-4）

## ADR-016：提醒调度用 setInterval 轮询，不复用 node-cron

- **日期**：2026-08-03（M12.5 v1.2 提醒）
- **状态**：已采纳
- **背景**：v1.2 提醒要定时触发。已有 ADR-012 的 node-cron（跟进调度）。是否复用 cron 做提醒？
- **决策**：提醒用 **setInterval 轮询**（每 60s 扫 reminders 表），不复用 cron。
- **理由**：
  - **语义不同**：跟进是"定点"（9:00/14:00），cron 表达式贴切；提醒是"任意到分"（用户随时设的"N 分钟后"），cron 表达式难以覆盖，轮询语义更贴切。
  - **实现简单**：`setInterval(tick, 60000)` 扫 `time<=now && done=0`，触发后标 done。无需为每个提醒算 cron 表达式。
  - **精度足够**：60s 轮询，提醒最多迟 1 分钟，用户无感。
- **否决项**：
  - 复用 node-cron——提醒时间任意，每条提醒一个 cron 表达式开销大且复杂。
- **后果**：scheduler.ts 加 `startReminderPoller`/`stopReminderPoller`，与 followup cron 并存（两套独立调度）。

## ADR-020：数据看板用 recharts + 独立 Tab + 消息聚合 IPC（v1.4）

- **日期**：2026-08-03（M14 v1.4）
- **状态**：已采纳
- **背景**：PRD §16.5/§16.6 推荐「数据看板」为 v2 高性价比方向（番茄钟/任务数据已具备，几乎免费的功能）。v1.3 概览页（M13.4）已是「今日快照」，看板需做「历史趋势」补位。
- **决策**：
  1. **图表库用 recharts 3.x**（+ peer dep react-is）。
  2. **独立「看板」Tab**，放侧栏概览之后（数据展示组：今日快照 → 历史趋势），不并入概览页。
  3. **pomodoro/tasks/reminders/notes 复用现有 list**（前端 reduce 聚合）；**messages 表走专属聚合 IPC `dashboard:activity`**，只回 date+count，不传 content 大字段。
  4. **时间范围切换 7天/30天/全部**（SegmentedSwitcher，复用给「趋势/分布」图表模式切换）。
  5. **图表模式切换（趋势/分布）**而非堆叠全部图——省纵向空间，每屏只看 2 图。
- **理由**：
  - **recharts 选型**：peerDependencies 明确含 `^19.0.0`（与项目 React 19.2.7 兼容，无需 overrides），声明式 API 语料丰富。echarts 体积 800KB 过重需 wrapper，纯 SVG 手画只能做简单图。recharts ~150KB 是平衡点。
  - **独立 Tab 不并概览**：概览是「今日快照」（默认首页 + 快捷入口，信息密度低），看板是「历史趋势」（多图 + 时间范围，信息密度高）。两种信息密度混在一页会让概览页变臃肿。职责分离。
  - **messages 走聚合 IPC**：messages 表随对话增长可能上千行，全量 `message:list` 拉回 content 大字段浪费。`GROUP BY date(created_at,'unixepoch')` 在主进程聚合，只回 `{date, count}[]`，体积恒定。
  - **模式切换不堆图**：4 个图（专注折线/任务柱状/状态饼图/时段柱状）全铺开要滚动。趋势/分布两组各 2 图，Tab 切换每屏看全，符合「数据看板一屏览」的预期。
  - **颜色读 CSS 变量**：`cssVar('--accent')` 读 HSL 分量转 `hsl()`，浅深主题自动跟随（recharts 不响应 CSS 变量，故监听 `theme.resolved` 改 key 重建图表）。
- **否决项**：
  - echarts——体积过大，需 wrapper，过度设计。
  - 看板嵌入概览页底部——信息密度冲突。
  - 任务「完成趋势」双柱——任务表无独立 completedAt 字段，用 updatedAt 近似完成日会误导（updatedAt 可能是改标题而非完成）。改为单柱「新建趋势」+ StatCard 用完成率体现，更诚实。
- **后果**：装 recharts + react-is；types 加 `DashboardRange`/`ActivityPoint`/`ActivityQuery`；preload + ipc + registerIpcHandlers 三处同步加 `dashboard:activity`；新增 `src/pages/dashboard/`（DashboardPage + charts）；nav Tab 加 `'dashboard'`；icons.ts 加 `Dashboard`（ChartBarIcon 别名）。

### 踩坑（v1.4 M14 新增，回写接手提示词）
- **recharts HMR 白屏**：新装 recharts 后首次 `import` 触发 vite 运行中 optimize → full reload，old/new chunk 竞态白屏。**修法：装完大依赖后重启 dev（清 `node_modules/.vite` 缓存），别依赖 HMR。** tsc 过 ≠ 运行时 OK。
- **react-refresh 组件改名报错**：把 `RangeSwitcher` 重构为泛型 `SegmentedSwitcher` 时，HMR 残留旧引用报 `RangeSwitcher is not defined`。**这是热更新瞬态错误，刷新/重启即消失，打包版不受影响。**

## ADR-021：全应用动效升级用 CSS animation，不引 GSAP/framer-motion（v1.5）

- **日期**：2026-08-03（v1.5）
- **状态**：已采纳
- **背景**：用户反馈 v1.3 Soft UI「页面还是太素」，要求动效多、贴合主题、禁蓝紫渐变。ui-ux-pro-max skill 调研推荐 hover 微交互（Standard tier：y:-4+scale+shadow）、scroll reveal（stagger 0.08s）、数字 count-up。
- **决策**：
  1. **动效全部用 CSS keyframes + requestAnimationFrame 实现**，不引 GSAP / framer-motion。
  2. **覆盖核心 4 页**（概览/对话/任务/看板）：header 电光蓝径向光晕（hero-glow）+ 标题/列表 fade-up 入场 + stagger 错峰 + 卡片 hover 浮起 + 数字 count-up + StatCard sparkline。
  3. **禁蓝紫渐变色**（用户原话）：光晕用单色电光蓝 `hsl(221 100% 50% / 0.08)` radial-gradient，非 linear-gradient 紫粉色块。
  4. **可复用基建**：`useCountUp` hook（src/lib/）、`Sparkline` 组件（src/components/ui/）、index.css 的 fade-up/hero-glow/count-pulse/stagger-fade-up 工具类。
- **理由**：
  - **不引 GSAP**：Electron 桌面应用体积考量（v1.3 已定调）。skill 的 gsap snippet 用 CSS transition + rAF 等价实现，零体积增加。framer-motion 同理。
  - **CSS 动效基建复用**：fade-up/stagger 工具类一次定义，4 页直接 className 引用，新增页面零成本。
  - **hover 不碰 border**：Tailwind v4 的 `border` 无颜色时默认 currentColor，`hover:border-accent/30` 会与 Card 自身 transition 冲突渲染异常（踩坑：图标下出现多余蓝线感）。**hover 只用 shadow + translate，不用 border 变色。**
  - **sparkline 数据门槛**：`< 2 个非零点` 或 `全相等` 时不渲染（平线 = 视觉噪音，无趋势信息）。
- **否决项**：
  - GSAP / framer-motion——体积 + Electron 打包考量。
  - 3D 倾斜 / magnetic 鼠标跟随（skill Complex tier）——桌面应用过度。
  - 蓝紫渐变背景——用户明确禁止。
- **后果**：新增 useCountUp + Sparkline；index.css 加 fade-up/count-pulse/hero-glow/stagger-fade-up（含 nth-child 错峰）；4 页 header 加 hero-glow + animate-fade-up；StatCard 接 count-up + hover:shadow-lg + sparkline；任务列表/快捷入口 stagger-fade-up；对话消息块 animate-fade-up。

## ADR-022：模型档位用 KV 存 JSON + 手动分层 + 会话级记忆（v1.6）

- **日期**：2026-08-04（M15 v1.6）
- **状态**：已采纳
- **背景**：PRD §16.3/§16.6 推荐「模型自动路由」为 v2 高性价比方向（简单任务用便宜模型，省钱）。但自动判定「简单/复杂」逻辑难调（PRD 原话），用户经确认选择「手动分层 + 自定义多档」——即语义化快捷分组，不做自动判定。
- **决策**：
  1. **手动分层**：用户在设置页定义任意档位（如「快型」→glm-flash、「强力」→glm-4.5），对话页 select 显示档位名，手动切换。**不做自动判定**。
  2. **数据存 settings KV `router.tiers` 的 JSON**（`[{"id","name","providerId"}]`），不建表。
  3. **会话级记忆**：复用闲置字段 `conversation.defaultProviderId`（schema 早已存在，ChatPage 此前未读）。
  4. **路由解析层预留**：`resolveProviderId(requested, ctx?)` 当前透传（档位 id→providerId），ctx 参数为未来自动路由预留。
- **理由**：
  - **手动而非自动**：自动路由（分类器/规则）复杂度高、易误判、需调参。手动分层零风险、立即有用（切换更直觉）。用户明确选择此方向。
  - **KV 存 JSON 不建表**：档位数量少（2-4 个）、字段简单（name+providerId）、无独立查询需求（每次全量读）。建表要两处同步 schema（schema.ts + BOOTSTRAP_SQL），KV 零迁移更轻。
  - **闲置字段复用**：`conversation.defaultProviderId` 在 M2 就定义了但 ChatPage 从未读取，是会话级记忆的天然挂载点，零 schema 改动。
  - **select value 用 providerId**：档位是 provider 的语义别名，select 的 value 始终是具体 providerId（档位的 providerId），无需额外 selectedTierId state。档位和 provider 绑同一 id 时 select 显示第一个匹配——可接受（档位是快捷方式非唯一标识）。
- **否决项**：
  - 自动路由（分类器/规则）——复杂度高，用户明确否决。
  - 建 model_tiers 表——两处同步 schema，过度设计。
  - 全局默认档位（非会话级）——会话场景差异大（闲聊 vs 写代码），会话级记忆更合理。
- **后果**：新增 tiers.ts（数据层）+ tiers store + RouterSection（设置页）+ router.ts（解析层 stub）；ChatPage select 加 optgroup 档位分组 + 切会话 hydrate defaultProviderId + handleProviderChange 同步更新 store；新增 IPC `conversation:setProvider`（三处同步）；chat:send 插入 resolveProviderId。

### 踩坑（v1.6 M15 新增，回写接手提示词）
- **切 provider 闪回旧值**：useEffect 依赖了 providerId，用户切 provider → providerId 变 → effect 重跑 → 读会话旧 defaultProviderId → 覆盖回去（"闪一下变回"）。**修法：hydrate useEffect 只依赖 activeId（只在切会话时跑），且 handleProviderChange 同步更新 chat store 的 conversations（保证 currentConv 准确）。**

## ADR-023：PDF 工具箱用 pdf-lib 纯客户端，压缩砍 v2、预览推迟（v1.7）

- **日期**：2026-08-04（M16 v1.7）
- **状态**：已采纳
- **背景**：PRD §15.4⑥ PDF 工具箱要求合/拆/提取 + 预览（pdfjs-dist）。原计划 v1.2 做，实际推迟到 v1.7。
- **决策**：

  2. **压缩砍 v2**（PRD 已明确：pdf-lib 无真压缩，只能重存+图片降质，真压缩需 Ghostscript WASM）。UI 标注 v2。
  3. **预览（pdfjs-dist 缩略图）推迟**：pdfjs-dist 的 worker 在 Electron+Vite 下配置是已知重灾区（worker 路径/CSP/打包解包），MVP 不做，后续增强。
  4. **独立于 converter 服务**：converter 是格式转换（md→pdf 生成），PDF 工具箱是页面操作（合/拆/提取），职责不同，不并入。
  5. **页码 UI 1-indexed / 内部 0-indexed**：用户输入「1,3,5-7」，服务层 `parsePageInput` 转 0-indexed 数组，容错非法输入。
- **理由**：
  - **pdf-lib 选型**：纯 JS 无 native，与 better-sqlite3/native 模块不同，打包不踩坑。API 成熟（create/load/copyPages/addPage/save）。
  - **不引 pdfjs-dist**：其 worker 配置在 Vite 下需 `new Worker(new URL(...))` + Electron 打包要 asarUnpack + CSP 调整，复杂度高。预览是加分项非核心，推迟避免阻塞 MVP。
  - **路径安全复用 converter 模式**：所有读写经 `resolveSafePath`（白名单/笔记库 + isSensitive 黑名单），照搬 converter 的 buildSourcesForConvert。
- **否决项**：
  - pdfjs-dist 预览——worker 配置坑，推迟。
  - Ghostscript WASM 压缩——依赖重，v2。
  - 并入 converter——职责混淆。
- **后果**：装 pdf-lib；新增 pdfToolbox.ts（服务）+ PdfToolbox.tsx（UI）+ 5 个 IPC（pdf:info/merge/extract/split/pickFile，三处同步）；types 加 PdfInfo/PdfResult/PdfSplitResult；icons.ts 加 FilePdf；ToolsPage 加 PDF 入口卡。

## ADR-024：老库加列用幂等 ALTER + PRAGMA table_info 探测（v1.8）

- **日期**：2026-08-04（M17 v1.8）
- **状态**：已采纳
- **背景**：v1.8 日报功能需要 task 的「精确完成时间」，tasks 表原本只有 `status='done'` 无 `completedAt`（dashboard charts.tsx 曾注释「用 updatedAt 近似完成日会误导」）。要加 `completed_at` 列。但项目无 drizzle-kit migrate 框架（M1 起用「启动时建表」策略，BOOTSTRAP_SQL 全 `CREATE TABLE IF NOT EXISTS`）——`IF NOT EXISTS` 对**新库**生效，但**老库**（用户已运行过的 app.db）表已存在，CREATE 不会补列。
- **决策**：
  1. **新库**：CREATE TABLE tasks 加 `completed_at INTEGER`（IF NOT EXISTS 自然覆盖）。
  2. **老库**：在 `getDb()` 的 `_raw.exec(BOOTSTRAP_SQL)` 之后，用 `_raw.pragma('table_info(tasks)')` 探测列是否存在，不含则 `_raw.exec('ALTER TABLE tasks ADD COLUMN completed_at INTEGER')`。
  3. **幂等**：PRAGMA 探测保证多次启动只 ALTER 一次（第二次列已存在跳过）。
- **理由**：
  - SQLite 的 `ALTER TABLE ADD COLUMN` 无 `IF NOT EXISTS` 语法（与 CREATE TABLE 不同），重复执行会报 `duplicate column name`。
  - PRAGMA table_info 是 SQLite 标准的 schema 内省接口，返回 `{name}[]`，可靠。
  - 不引 drizzle-kit migrate：项目「全靠 AI 写代码、出错率低」第一约束下，迁移文件管理（版本号/顺序/回滚）是额外复杂度，启动时探测更简单可控。
- **模式固化**：后续再加列照抄此块，换表名/列名/DDL。已回写 AGENTS.md §6 两处同步清单。
- **后果**：db/index.ts getDb() 加迁移块；schema.ts + BOOTSTRAP_SQL CREATE 都加列（两处同步照旧）；老库首次启动 v1.8 自动补列，日志 `[db] 迁移：tasks 已加列 completed_at`。

## ADR-025：AI 报告复用笔记库 + tag，不建 ReportRecord 表（v1.8）

- **日期**：2026-08-04（M17 v1.8）
- **状态**：已采纳
- **背景**：PRD §15.3④ AI 日报/周报，§15.6 数据模型设计了 `ReportRecord` 表（id/type/dateRange/notePath/createdAt）。但报告本身已是 .md 笔记（noteStore.createNote 写入笔记库，有 frontmatter id/title/tags/时间戳），建表会与笔记库数据重复。
- **决策**：报告写成 .md 笔记存入笔记库，tag 用 `['日报']`/`['周报']` 区分类型，标题带日期（`日报 2026-08-04`/`周报 2026-08-04~2026-08-10`）。历史报告用 `note:list` + tag 过滤，不建 ReportRecord 表。
- **理由**：
  - **数据复用优先**（项目核心原则，v1.4/v1.6 一贯）：报告已是结构化笔记，再建索引表是冗余。
  - **零迁移**：不建表 = 不动 schema/BOOTSTRAP_SQL，降低出错面。
  - **天然可编辑/搜索**：报告就是笔记，用户可在笔记页直接编辑/全文搜，A/B 轨天然共享（双轨制 ADR-013 的关键约束）。
  - **PRD ReportRecord 是 P1**：表设计本就是可选，tag 方案满足 MVP。
- **否决项**：建 ReportRecord 表——与笔记库数据重复，违反复用优先；列表去重等增强留 v2。
- **后果**：不新增表；reportGenerator.ts 只产 Markdown；report:generate IPC 调 noteStore.createNote 写入；ReportToolbox 用 notes store 过滤 tag 列历史。types 加 ReportPayload/ReportGenerateParams/ReportResult（不含表映射）。

## ADR-026：截图标注用 desktopCapturer 主进程调 + 原生 canvas，不上 fabric/konva（v1.19）

- **日期**：2026-08-07（v1.19，PRD §15.4⑧ 收官）
- **状态**：已采纳
- **背景**：PRD §15.4⑧ 截图标注是「文档/文件增强组」最后一个（⑥PDF 工具箱/⑦OCR 已完成）。要求：desktopCapturer 截屏 + 画框/箭头/文字标注 + 复制剪贴板/存工作目录/拖入对话。PRD §15.5 已明确「不上 fabric.js（无官方 React wrapper，状态同步痛点），原生 canvas AI 生成出错率最低」。TV-8 验证项：生产构建（非 dev）能截屏。
- **决策**：
  1. **desktopCapturer 在主进程调**：项目安全三件套（contextIsolation:true + nodeIntegration:false + sandbox:true）下渲染层拿不到 desktopCapturer，必须走 IPC。主进程 `captureScreen()` 用 `desktopCapturer.getSources({types:['screen']})` + `thumbnail.toPNG()` → dataUrl 返渲染层。
  2. **标注用原生 canvas 2D API**：shape 数据结构 `{type:'rect'|'arrow'|'pen'|'text', ...}`，重绘 = clearRect + drawImage 底图 + 正序重放 shapes。撤销 = pop。零依赖（不上 fabric/konva/excalidraw）。
  3. **工具页内嵌形态**（不做全屏遮罩/快捷键）：进工具页点「截取屏幕」→ 返 dataUrl → 页内 canvas 标注 → 三去向。架构最轻，多显示器遮罩拼接是坑故推迟。
  4. **标注图保存照搬 note:save_image**：dataUrl → Buffer → 笔记库 images/ 落盘，路径应用自决不经 resolveSafePath（同贴图模式）。
  5. **剪贴板走主进程 IPC**：项目首次用 `clipboard.writeImage`（渲染层 clipboard API 受沙箱限）。
  6. **插入对话走跨页 zustand store**：新建 `src/stores/screenshot.ts`（订阅式，因 ChatPage 常驻挂载 v1.17.1），复刻 followup:open 跨页跳转范式。
  7. **颜色固定电光蓝 accent**（遵守「统一蓝不色彩泛滥」红线），粗细 2/4/6px 三档，不做颜色自定义。
  8. **多显示器限制写进 UI**：Chromium 无法整屏拼接多屏，仅截主屏（screen.getPrimaryDisplay），UI 文字提示。
- **理由**：
  - **遵循 PRD 既定方向**：PRD §15.4⑧ + §15.5 已明确 desktopCapturer + 原生 canvas，不上 fabric。原生 canvas 的交互工作量在 mouseEvent 坐标换算 + shape 重绘，AI 生成代码出错率最低（PRD 原话）。
  - **主进程调 desktopCapturer 是安全三件套的必然**：sandbox:true 下渲染层无 Electron API 访问权。
  - **跨页 store 订阅式**：ChatPage 用 hidden 控制显隐不 unmount（v1.17.1），mount-once 读不到后续 push，必须 useEffect 订阅 store 变化。store 空态用模块级 EMPTY 常量保证引用稳定（照搬 chat.ts IDLE_META 范式）。
  - **P0 工具集四件套**：矩形框/箭头/文字/画笔 + 撤销。画笔自由曲线替代马赛克（马赛克像素采样复杂，画笔覆盖大部分标注需求）。无重做（撤销够用，省一半复杂度）。
- **否决项**：
  - fabric.js / konva / react-konva——PRD 明确否决，且会破坏「零依赖」优势。
  - 全屏遮罩框选 + 全局快捷键——架构重（新建全屏 BrowserWindow + 快捷键注册），多显示器遮罩拼接是坑，推迟。
  - 马赛克——P1，像素采样实现复杂，画笔已覆盖标注需求。
  - 区域裁剪——整屏截取后画笔标注即可，不做框选裁剪子区域。
- **后果**：新增 screenShot.ts（服务）+ ScreenshotToolbox.tsx（UI）+ screenshot.ts（跨页 store）；ipc/index.ts 加 registerScreenHandlers（screen:capture/save/copy_clipboard，三处同步）；ChatPage 加 useEffect 订阅 screenshot store；icons.ts 加 Screenshot/FrameCorners/ArrowUp/TextT/PaintBrush 等（Phosphor 无 ScreenshotIcon，用 ScreencastIcon 别名）；ToolsPage 加入口卡。零新依赖，electron-builder.json 无需改。TV-8 待打包版真机验证。

## 技术验证实测结论（M1）

### TV-1：智谱 GLM 是否支持 Function Calling
- **结论**：✅ **支持**。GLM-4 / 4.5 / 4.5-Air / 4.6 / 5 全系列在 OpenAI 兼容端点 `https://open.bigmodel.cn/api/paas/v4/chat/completions` 上完整支持 `tools` / `tool_choice`，schema 与 OpenAI 一致。
- **唯一限制**：新的 `/responses` API 尚未支持（见 ADR-003），但我们不用它。
- **依据**：[智谱 OpenAI 兼容文档](https://docs.bigmodel.cn/cn/guide/develop/openai/introduction)。
- **影响**：FC 依赖的功能（任务抽取/状态修改/搜索/文件）全部成立，TV-1 风险消除。

### TV-2：智谱 vs DeepSeek 用于抽取/跟进
- **结论**：两者均支持 FC。
  - DeepSeek `deepseek-chat`（V3）支持 FC，社区反馈偶有不稳定，最大输出 8192 tokens；`deepseek-reasoner`（R1）**不支持** tools。
  - 智谱 GLM-4.5-Air / 4-Flash 更适合做廉价后台调用（抽取/跟进）。
- **决策**：跟进/抽取默认走智谱 Flash 档或 deepseek-chat，设置里可指定。

### DeepSeek 兼容性确认
- `baseURL='https://api.deepseek.com'`（或 `/v1`），OpenAI SDK 直接用，model `deepseek-chat`。
- 依据：[DeepSeek API Docs](https://api-docs.deepseek.com/)。

### TV-3：见 ADR-002（两家都接，M5 实现）。
